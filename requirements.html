1. Purpose and scope

Automated-vehicle software is tested on a desktop, on the target computer and on the vehicle. Each stage usually keeps its own copy of every test, so tests are rebuilt several times and results cannot be compared. CSTI lets one scenario run unchanged in four stages:

MiL (Model-in-the-Loop)
Controls: Simulink controllers against RoadRunner Scenario, with objects taken straight from RoadRunner, unprocessed. Perception: sensor placement and specs checked in RoadRunner, with AURELION adding realistic sensor data and sensor faults on the desktop. No fusion on the vehicle stack and no safety interlock.
PiL (Processor-in-the-Loop)
Controls: each Simulink controller is code-generated separately into a C++ ROS 2 node on the AUTERA AutoBox, fed RoadRunner ground truth over ROS 2. Perception: RTMaps and the C++ object fusion run on the AUTERA, fed AURELION simulated sensor data from the desktop.
HIL (Hardware-in-the-Loop)
The sensor cart: real sensors on a cart feed RTMaps and the full stack on the AUTERA with its safety interlock active, while the Simulink vehicle model on the HIL bench receives the stack’s Ethernet commands.
ViL (Vehicle-in-the-Loop)
The production vehicle on a closed course with real sensors, a safety driver and the full safety chain, with virtual actors injected around its real position.

The autonomy stack is outside CSTI. CSTI feeds its inputs, records its outputs and never commands actuators. A shadow profile runs the stack live without engaging automation.

3. Conventions

  • Names. Each requirement has a unique name used on every page. Groups: Functional, Non-functional, Safety and Constraints.
  • Priority. Must required; Should expected but not essential.
  • Verification. T test, A analysis, I inspection, D demonstration.
  • Numbers. Every threshold is a team proposal, linked to the proposed values table.
  • Provisional. Sensor mounting, actuation limits, override thresholds and where camera detection and LiDAR clustering run are not yet settled.

4. Constraints and assumptions

NameConstraint or assumption
ROS 2 stack in one containerThe stack runs on the target computer in one container: an ingest middleware syncs and preprocesses sensor data, and ROS 2 does object fusion and the rest. CSTI connects through ROS 2 topics at fusion's inputs.
Stack not modifiedThe stack is not modified for CSTI, apart from launch-time topic remapping.
Generic hardware, public siteHardware is described generically; no vehicle-specific or confidential data appears on this public site.
Closed course with safety driverViL runs only on a closed course with a safety driver. The vehicle's override, E-stop, mode switch and actuation gateway stay in place, and CSTI never commands them.
Vehicle localization on ROS 2The vehicle publishes its position, heading, velocity and uncertainty on a ROS 2 topic.
No single vendor formatCSTI must work with more than one simulator and cannot depend on one vendor's format.

7. Safety requirements

Safety principle. CSTI has no safety role. Safety belongs to the stack: a fault detection node watches critical systems, the ACC, LCC and AIN state machines watch for driver overrides, and the safety interlock sends default commands and alerts the driver on any fault. CSTI only adds objects that are not there, listens to the stack's status, and stops injecting when the stack or the operator says so.

NameRequirementAcceptance criterionVer.PrioritySource

10. How requirements are tracked

Each requirement is tracked through the stages with MathWorks tools. Test cases in Simulink Test Manager run RoadRunner scenarios against the Simulink models, one test case or iteration per scenario and variant (RoadRunner test cases). Requirements live in Requirements Toolbox, imported from the team's Excel sheet (Excel import), and each one is linked to the test cases that verify it, so its pass or fail status updates after every run (linking tests). Results from HIL and the vehicle, which run outside Simulink, can feed the same status as JUnit or Excel result files (external results). As scenes are rebuilt from real map data collected on the car, the same test cases rerun on them, so every failure stays tied to a requirement, a scenario and a software version.

11. Open issues

  1. Stack behavior when injection stops. Resolved by Stop injecting on a stack fault: CSTI removes all virtual objects at once, and the stack's safety interlock sends default commands and alerts the driver.
  2. Where virtual and real data meet. Resolved by Injection on fusion's existing topics: on fusion's existing topics, with a logging copy.
  3. Raw data in ViL. Resolved by Object-level injection in ViL: object lists only.
  4. Unmeasured values. 50 ms (proposed), 1 ms (proposed) and 0.20 m (proposed) depend on hardware not yet measured.
  5. Provisional inputs. Sensor mounting, actuation limits, override thresholds, and camera detection and LiDAR clustering locations.
