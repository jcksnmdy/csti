Backend Adapters

Design › Backend Adapters

ResponsibilityConnect each simulator to CSTI through one common plug-in interface.
Tool category«tool» Simulink vehicle dynamics model; AURELION sensor simulation
OwnerMember 3
GroupSimulation runtime
DeploymentDesktop or in-vehicle test computer, by stage
ProvidesBackend adapter interface
RequiresRun control, Actor states, Clock and sync health

Description

Simulators only render actors and model sensors; CSTI decides what the actors do. Only the adapters touch simulator-specific code, so a simulator can be added or replaced without changing anything else.

Sub-components

NameRole
Desktop simulator (MiL)Simulink controllers and vehicle dynamics model on a desktop, co-simulated with the RoadRunner scenario.
RoadRunner publisher (PiL)For controls PiL: RoadRunner Scenario, co-simulating in Simulink, publishes ground truth (ego odometry, actor positions) to the ROS 2 network, where the code-generated controller nodes run.
Sensor simulator (perception MiL, PiL)AURELION co-simulates the RoadRunner scenario on the desktop (VEOS), producing realistic sensor data and sensor faults. An AURELION Setup block in Simulink sends the ego and fellow-vehicle poses. In MiL the data stays on the desktop; in perception PiL it feeds RTMaps on the AUTERA.
Sensor cart (HIL)Real sensors on a cart feed RTMaps and the stack on the AUTERA; CSTI adds only virtual objects and faults on its own streams.
Headless player (ViL)Object-level data only, placed around the real vehicle's pose.

Key behaviors

  • Each adapter declares what it supports, so unsupported scenarios are rejected up front.

Stage variation

Desktop simulator in controls MiL, sensor simulator in perception MiL and PiL, RoadRunner publisher in controls PiL, sensor cart in HIL, headless player in ViL.

Failure behavior

A stalled adapter stops injection and fails the run.

Requirements satisfied (7)

  • Same scenario in every stage (supporting)
  • Three simulation backends (primary)
  • Stage selection by configuration (supporting)
  • Two sensor fidelity levels (object level and raw) (supporting)
  • Plant-model ego (MiL, PiL, HIL) (supporting)
  • New backend = new adapter only (primary)
  • Vendor dependencies only in adapters (primary)

  • Adapter pattern
