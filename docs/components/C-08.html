Fault Injector

Design › Fault Injector

ResponsibilityAdd scheduled faults to test how the stack copes with bad data.
Tool category«tool» Fault injection tool
OwnerMember 4
GroupSimulation runtime
DeploymentDesktop in MiL; on the bench and vehicle, a separate Intrepid data logger
Provides—
RequiresSynthetic sensor frames, Fault schedule

Description

Faults include added latency, noise, dropouts, ghost targets and frame drops on sensor streams, and, off the vehicle only, network faults, GNSS outages and actuator faults. In MiL it adds AURELION sensor faults; in HIL it also drops heartbeats and sensor streams to check that the stack's fault detection node and safety interlock respond correctly. Every fault is recorded with its timing.

Key behaviors

  • Seeded, so faulted desktop runs repeat exactly.

Stage variation

All faults in MiL, PiL and HIL; on the vehicle, only faults on CSTI's own virtual data.

Failure behavior

If it fails, the stream stops and the run is treated as missing data.

Requirements satisfied (6)

  • Sensor fault injection (primary)
  • Network, GNSS and actuator faults (primary)
  • Portable across nodes (supporting)
  • Deterministic MiL runs (supporting)
  • CSTI cannot affect the stack's safety chain (supporting)
  • Vehicle-test faults limited to virtual streams (supporting)
