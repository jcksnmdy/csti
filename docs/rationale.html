Decisions

Simulator-agnostic scenario format

Requirements: Single scenario definition, Same scenario in every stage, Open, simulator-independent formats, Vendor dependencies only in adapters, New-user onboarding time · Components: Scenario Model, Scenario Validator

Issue
Every stage must run the same test, but each tool has its own scenario format.
Options considered
  • One vendor's format as master. Good tools, but locks every other simulator to an exporter.
  • A custom CSTI language. Full control, but no tool support.
  • Open OpenDRIVE and OpenSCENARIO files with a CSTI subset. Open and widely supported; features vary between tools.
Decision
Author in RoadRunner, but treat the exported OpenDRIVE and OpenSCENARIO files, limited to a subset every simulator supports, as the source of truth.
Justification
It is the only option where the test belongs to no single tool. Features outside the subset are rejected before the run instead of behaving differently per simulator.
Trade-offs accepted
Authors cannot use features only one simulator supports.

Adapter pattern instead of one simulator for everything

Requirements: Three simulation backends, Stage selection by configuration, New backend = new adapter only, Vendor dependencies only in adapters · Components: Backend Adapters, Test Orchestrator

Issue
No single simulator is fast for campaigns, realistic for sensors and usable on the vehicle.
Options considered
  • One simulator everywhere. Simplest, but too slow or unusable on the vehicle.
  • One plug-in adapter per simulator. One adapter to write per simulator; nothing else changes.
Decision
Put each simulator behind the same plug-in interface.
Justification
Adding or replacing a simulator then touches only its adapter.
Trade-offs accepted
The interface only offers what all simulators can do.

CSTI owns actor behavior

Requirements: Backend-independent actor state, Real-pose ego and placement (ViL), Deterministic MiL runs, New backend = new adapter only · Components: Actor Manager, Backend Adapters, Trigger Engine

Issue
If each simulator moves the actors, the same test behaves differently per simulator, and the vehicle stage has no simulator at all.
Options considered
  • Each simulator moves its own actors. Mature behaviors, but different motion per tool.
  • CSTI computes actor motion and sends it to the simulator. Same motion everywhere; CSTI implements the behaviors.
Decision
CSTI computes actor motion; simulators only draw actors and model sensors.
Justification
It gives identical motion on every simulator and on the vehicle, and repeatable desktop runs.
Trade-offs accepted
CSTI's behaviors are simpler than a commercial traffic model, which is enough for scripted tests.

Object-level injection in ViL

Requirements: Two sensor fidelity levels (object level and raw), Injection latency limit, Full rate with many actors, Virtual-actor placement accuracy · Components: Sensor Abstraction Layer, Backend Adapters

Issue
Raw simulated images test the whole perception chain but are too slow to generate on the vehicle.
Options considered
  • Raw data in every stage. Most realistic; misses the vehicle's latency budget.
  • Object level on the vehicle, raw data on the bench. Fits the budget; the vehicle stage does not test detection.
Decision
Inject object lists in HIL and on the vehicle, and raw data only in MiL and PiL.
Justification
Object lists fit the 50 ms budget; detection is still tested on the bench.
Trade-offs accepted
Vehicle tests exercise planning and control, not detection of virtual objects.

One clock master per stage

Requirements: Clock offset limit, Deterministic MiL runs, Faithful replay timing, Replay any run in MiL · Components: Time & Sync Service, Ego-State Bridge

Issue
Mixed clocks make timestamps meaningless and runs unrepeatable.
Options considered
  • Each part uses its own clock. No setup; no comparable timing.
  • Simulated time everywhere. Repeatable; impossible on the real vehicle.
  • One clock per stage. Simulated time on the desktop, real time on HIL and the vehicle.
Decision
Use one clock per stage: simulated time in MiL and PiL, real time in HIL, GNSS time in ViL.
Justification
Simulated time makes desktop runs repeatable; GNSS time gives the vehicle and the ingest middleware one shared reference.
Trade-offs accepted
Real-time runs are not repeatable, so they rely on full recording for replay.

Frozen stack contract

Requirements: Same topics as real sensors, /virtual/ mirror, New sensor = add-only change, Same scenario in every stage, Stack not modified · Components: Stack Interface Gateway, Sensor Abstraction Layer

Issue
If the interface to the stack changes between stages or releases, the stack cannot be tested the same way everywhere.
Options considered
  • Adapt the interface per stage. Flexible; the stack would need stage-specific code.
  • Freeze it and allow only additions. Stable; new needs must be added, never changed.
Decision
Freeze the topic contract; it can only grow.
Justification
The stack depends on one thing in CSTI, and that thing does not change.
Trade-offs accepted
A mistake in the contract can be retired but never edited.

Inject on fusion's existing topics

Requirements: Real sensor data never altered, Same topics as real sensors, /virtual/ mirror, Stack not modified · Components: Stack Interface Gateway, Sensor Abstraction Layer

Issue
Virtual detections must reach fusion without touching real sensor data or changing the stack.
Options considered
  • Merge node in front of fusion. Puts CSTI in the real-data path.
  • Separate virtual topics fusion must also read. Keeps data apart; fusion needs a special case.
  • Publish on fusion's existing topics, marked as virtual and copied to a log topic. No special case; two publishers share a topic on the vehicle.
Decision
Publish virtual data on fusion's existing input topics, marked as virtual and copied to a logging topic.
Justification
Fusion runs unchanged in every stage, and CSTI never handles real data.
Trade-offs accepted
Fusion must accept real and virtual data on the same topic.

CSTI has no safety authority

Requirements: CSTI cannot affect the stack's safety chain, Stop injection on stack fault or override, Start injection only when the stack is ready, Record stack faults and state changes · Components: Test Orchestrator, Stack Interface Gateway, Monitoring & Operator View

Issue
A test tool that can also stop or steer the vehicle becomes a second safety system that can disagree with the stack's own.
Options considered
  • A CSTI safety supervisor. Independent checks; a second authority to keep consistent with the stack.
  • The stack's own fault detection, state machines and safety interlock. One authority, the one that ships; CSTI depends on the stack's status.
Decision
The stack's fault detection node, feature state machines and safety interlock are the only safety chain; CSTI only listens to the stack's status and stops injecting.
Justification
There is one safety authority, the one that ships, and no second system to disagree with it.
Trade-offs accepted
CSTI depends on the stack reporting its status correctly.

On a stack fault, stop injecting and let the interlock act

Requirements: Stop injection on stack fault or override, Stop injection on operator command, Record stack faults and state changes · Components: Stack Interface Gateway, Test Orchestrator, Recording & Replay

Issue
When the stack faults, virtual actors could keep influencing it.
Options considered
  • Hold the last actors briefly. Smoother, but keeps feeding the stack during a fault.
  • Stop all virtual data at once. Abrupt but predictable.
Decision
Stop all virtual data at once and record why; the safety interlock sends default commands and alerts the driver.
Justification
The stack's response to its own fault should not be mixed with test input.
Trade-offs accepted
The stack sees virtual actors vanish at the moment of the fault.

Record everything at the interface

Requirements: Complete timestamped recording, Replay any run in MiL, Zero-drop recording, Verdicts linked to recordings, MCAP and CAN log recordings · Components: Recording & Replay, Run Evaluator

Issue
Selective logging risks missing the one signal that explains a failure.
Options considered
  • Record only outputs and scored signals. Small files; runs cannot be replayed.
  • Record every interface message and the run settings. Large files; complete evidence.
Decision
Record everything, except raw desktop data that can be regenerated from the run settings.
Justification
Replay and test evidence both need the full input sequence.
Trade-offs accepted
Vehicle recordings grow large.

Run-lifecycle state machine

Requirements: One-action run start, Start injection only when the stack is ready, Unattended campaigns, Always-visible stop control · Components: Test Orchestrator, Monitoring & Operator View

Issue
On the bench and the vehicle, the order of run steps matters.
Options considered
  • Scripts per test. Fast to write; hard to review.
  • Behavior tree. Flexible; hard to check exhaustively.
  • One explicit state machine. Every state and transition can be tested.
Decision
Every run follows one explicit state machine.
Justification
Starting and stopping injection only make sense if the system is always in one known state.
Trade-offs accepted
Unusual test flows must be built from ordinary runs.

Validate before the run

Requirements: Pre-run validation and ODD check, No pop-in actors, Vehicle-test faults limited to virtual streams · Components: Scenario Validator, Trigger Engine, Fault Injector

Issue
Many problems can be caught before a run starts.
Options considered
  • Each part checks itself at start-up. No central check; errors surface mid-run.
  • One validator before the run. One complete report first.
Decision
Check every scenario in one place before the run.
Justification
Errors are caught at a desk instead of on the track.
Trade-offs accepted
Anything the scenario cannot predict is left to the stack's own safety chain.

Pose extrapolation

Requirements: Injection latency limit, Virtual-actor placement accuracy, Real-pose ego and placement (ViL) · Components: Ego-State Bridge

Issue
By the time virtual data reaches the stack, the real vehicle has moved on.
Options considered
  • Use the latest pose. Simple; delay becomes placement error.
  • Project the pose forward to delivery time. Cancels most of the error.
Decision
Project the vehicle's pose forward to when the data will be delivered.
Justification
Delay is the largest part of the placement error budget.
Trade-offs accepted
Projection is less accurate during hard braking or steering.

Ingest middleware for synchronization; object fusion in ROS 2

Requirements: Same topics as real sensors, /virtual/ mirror, Injection latency limit, Real sensor data never altered, ROS 2 stack in one container · Components: Stack Interface Gateway, Backend Adapters

Issue
The existing Python fusion is too slow, and sensor work exists in both RTMaps and ROS 2.
Options considered
  • Split sensors across both. Reuses everything; needs bridging and two clocks.
  • Everything in ROS 2. One framework; manual time alignment.
  • RTMaps for every sensor, ROS 2 for object fusion. Each job where it fits; data flows one way.
Decision
RTMaps receives, synchronizes and preprocesses every sensor; ROS 2 fuses the objects in C++.
Justification
Time alignment and point clouds suit the middleware, while object lists are small enough for ROS 2.
Trade-offs accepted
CSTI's virtual data skips RTMaps, so CSTI must timestamp it on the same GNSS clock.

How the design evolved

TopicWhat changed and why
Injection path (Injection on fusion's existing topics)Virtual data moved from separate topics back onto fusion's own topics, so fusion needs no special case.
StagesPiL and HIL were split into separate stages.
Recording scope (Record everything)Vehicle runs also record real sensor data, so they can be replayed on the desktop.
Safety (CSTI has no safety authority)Safety moved out of CSTI into the stack's existing fault detection, state machines and safety interlock.
Stop behavior (Stop injecting on a stack fault)Holding virtual actors after a fault was rejected; CSTI stops and the interlock acts.
