Glossary

Terms and abbreviations used on this site.

Actor
A simulated vehicle, motorcycle or pedestrian.
Actuation gateway ECU
The vehicle unit that receives steering, braking and acceleration commands from the stack over automotive Ethernet, passes them to the actuators, and can disable automation on its own.
Adapter
The plug-in that connects one simulator to CSTI.
AURELION
dSPACE sensor simulator; the team uses it on the desktop for perception MiL and PiL, to produce realistic sensor data and add sensor faults.
AURELION Setup block
Simulink block that runs the AURELION co-simulation: it loads the AURELION project and the RoadRunner glTF road, and sends the ego and fellow-vehicle poses.
Autonomy stack
The software under test, from fusion to the vehicle interface.
Backend
A simulator, or the headless player, behind an adapter.
Campaign
One scenario run many times over a parameter sweep.
Contract (stack interface)
The fixed set of topics through which CSTI feeds the stack.
Ego
The vehicle under test.
Fault detection node
The stack part that watches heartbeats of critical systems and raises lateral, longitudinal, V2X and other faults.
Feature state machines
The ACC, LCC and AIN state machines; they monitor driver overrides and move to a faulted state on a fault.
Fidelity level
Object level (object lists) or raw (images, point clouds and similar).
Headless player
The vehicle-stage backend, which places virtual actors without rendering anything.
HIL
Hardware-in-the-loop: the sensor cart's real sensors feed RTMaps and the full stack on the AUTERA, with the safety interlock active and the Simulink vehicle model on the bench.
Ingest middleware
RTMaps, which receives, time-synchronizes and preprocesses every sensor before ROS 2.
Injection
Delivering virtual data to the stack.
MCAP
The open file format for recorded ROS 2 data.
MiL
Model-in-the-loop: Simulink controllers and RoadRunner sensor-placement checks on a desktop; no safety interlock.
ODD
Operational design domain: the roads, speeds and weather the stack is designed for.
OpenDRIVE / OpenSCENARIO
Open standards for road networks and scenario content.
PiL
Processor-in-the-loop on the AUTERA: code-generated C++ controller nodes fed RoadRunner ground truth (controls), and RTMaps plus object fusion fed AURELION data (perception).
Profile (run / vehicle)
Settings that choose the stage or describe a vehicle.
PTP
Precision Time Protocol, used to share GNSS time across computers.
REP-105
The ROS convention for vehicle coordinate frames.
Replay
Re-running a recording's inputs on the desktop.
RoadRunner
MathWorks tool for building road scenes and scenarios; exports OpenDRIVE, glTF and OpenSCENARIO.
ROS 2
The middleware the stack uses for object fusion and everything after it.
Run
One execution of one scenario in one stage.
Safety Interlock Manager
The stack part that listens to the feature state machines and, on a fault, sends default commands and alerts the driver.
Scenario
The single definition of a test.
Sensor cart
Real sensors mounted on a cart, used in HIL to feed the stack real data before it goes on the car.
Shadow mode
A run where the stack drives nothing and its would-have commands are logged.
Stage
MiL, PiL, HIL or ViL.
Touring mode
A mode in which any failure defaults the interlock to dummy commands and a dashboard alert.
Trigger
A scenario condition that starts an action.
V-ESI
Virtual Environment Sensor Interface: Simulink blocks that receive AURELION sensor data (radar detections, LiDAR points, camera images).
V2X
Radio messages between vehicles and infrastructure.
VEOS / SCALEXIO
dSPACE's PC-based simulation platform and its real-time HIL system.
Verdict
A run's outcome: pass, fail, stopped or invalid.
ViL
Vehicle-in-the-loop: the production vehicle on a closed course, with real sensors, a safety driver and the full safety chain, plus virtual actors.
