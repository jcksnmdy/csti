1. What sensor fusion means here

Sensor fusion turns every sensor's reports into one tracked list of objects around the vehicle, each with position, velocity, size, class and confidence. This vehicle uses object-level fusion: each sensor's data is first reduced to a list of objects, then the lists are combined. RTMaps prepares the data; ROS 2 fuses the objects.

StepWhereWhat it does

Camera preprocessing and detectionRTMaps (detector location to confirm)Turns images into an object list.
LiDAR sync and downsamplingRTMapsReduces point clouds before clustering into objects (clustering location to confirm).
Transform to vehicle frameROS 2Puts every detection in the vehicle's coordinates.
AssociationROS 2Matches detections to each other and to existing tracks.
Tracking filterROS 2Updates each object's position and velocity estimate.
Track managementROS 2Creates, confirms, deletes and prioritizes tracks for planning.

3. Where CSTI connects

In the data path (rejected): real sensor data passes through a CSTI node that merges in virtual objects. If CSTI fails, real detections are lost too.

Same topic, separate publisher (chosen): the real path is untouched. The CSTI gateway publishes virtual object lists on fusion's existing input topics, marked with a virtual source id and copied to /virtual/ for logs. If CSTI fails, only the virtual objects stop, and fusion runs unchanged in every stage (Injection on fusion's existing topics, Same topics as real sensors, /virtual/ mirror, Real sensor data never altered).

What this asks of the stack: fusion must accept real and virtual object lists on the same topic. CSTI's virtual object lists go through RTMaps like any other input, unless CSTI already timestamps them on RTMaps' time base; only then may they enter at fusion's inputs. Either way, the RTMaps pipeline itself is validated twice: first in perception PiL with AURELION's simulated sensor data, then in HIL with the sensor cart's real data.

4. Simulation chain

The team's simulation loop joins RoadRunner, a MathWorks vehicle dynamics model in Simulink, and AURELION on the desktop (VEOS). It serves perception MiL and PiL; HIL uses the sensor cart's real sensors instead.

StepToolWhat happens
Build scene and scenarioRoadRunnerExports the road as glTF for AURELION and OpenDRIVE, and the scenario as OpenSCENARIO (scene export, scenario export).
Drive the vehicleSimulinkThe controllers and vehicle dynamics model compute the ego pose each step.
Run the co-simulationAURELION Setup blockSends ego and fellow-vehicle poses to AURELION and keeps both sides in step at the update rate (20 ms in the team's setup).
Render sensorsAURELIONCamera, radar, LiDAR and ultrasonic data; radar can also output detections or object lists (AURELION).
Return sensor dataV-ESI blocks or RTMapsV-ESI blocks bring data into Simulink for controls tests; RTMaps brings it to the ROS 2 stack on the AUTERA for perception PiL.

MiL, controls: the Simulink controllers run against RoadRunner Scenario, taking its objects straight as ground truth, unprocessed. Scenes can be rebuilt from the team's drive data (camera example, LiDAR example), and RoadRunner Scenario can generate scenarios from recordings, generate variations and automate test runs.

MiL, perception: sensor placement and specs are checked in RoadRunner. AURELION co-simulates the same scenario on the desktop to produce realistic sensor data and to add sensor faults. This is still MiL.

PiL, controls: each Simulink controller is code-generated separately into a C++ ROS 2 node on the AUTERA, fed RoadRunner ground truth such as ego odometry and actor positions over ROS 2 (MathWorks example).

PiL, perception: RTMaps and the C++ object fusion run on the AUTERA, fed AURELION's simulated sensor data from the desktop through RTMaps (dSPACE integration examples). How AURELION's output reaches the AUTERA is to confirm.

HIL, the sensor cart: real sensors on a cart feed RTMaps and the full stack on the AUTERA, with the safety interlock active. The stack commands steering, braking and acceleration over automotive Ethernet, as on the car, and the Simulink vehicle model on the HIL bench receives those commands, so the real vehicle interface is tested too. CSTI adds virtual objects through its gateway.

To check: the V-ESI update rate sets the simulated sensor rate; it should match each real sensor's rate so perception PiL sees the same timing as the car.
